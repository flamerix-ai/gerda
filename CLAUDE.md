# CLAUDE.md

Agent-facing guide for Claude Code (claude.ai/code) working in this repository. Humans start at [README.md](README.md).

## What this is

Two parts. **Gerda, the harness** (`harness/` + host tooling): a framework for writing and running bot code inside Minecraft on the **jsMacros** mod — TCP bridge, MCP server, eyes/hands primitives, and a worker that eval-loads ANY `Module` object (init/tick/command/stop; plain-JS skeleton: `harness/bot_template.js`) and drives it tick by tick. **Gerda Bot** (`src/`): our reference implementation of that contract — an autonomous GregTech (GTCEu) ore-mining bot (Monifactory modpack, Forge 1.20.1): vein detection, tool-aware breaking, ore-priority selection, inventory dump cycles, hot-swap, error recovery. Movement is the bot's own navigator; Baritone exists only as an optional chat-command passthrough.

The runtime is **GraalJS (ECMAScript 2022)**. `src/` is a TypeScript kernel compiled to one eval-loadable bundle; write modern TS.

**Extending the bot** — read **`docs/EXTENDING.md`** first: missions/plans/capabilities, growing the harness via ext plugins, the SRG-mapping workflow, the Runtime facade contract.

**Driving the live co-op fleet** — read **`docs/FLEET_PLAYBOOK.md`**. Core rule: **bots play as real non-op players.** The only admin action used on them is teleport; do not hand them items or reach for `/give`, `/setblock`, `/summon` — the server refuses those from non-op clients anyway. The playbook covers `target=`/`mc_fleet_*` driving, the FTB-quest workflow (`quest_complete`/`quest_claim` + `scripts/objective/`), legitimate prospector recharge (Turbo Charger, EU), and why bots don't see players. The server that `docs/SERVER_SETUP.md` sets up is always-day, peaceful, online-mode off.

**Booting clients off-screen (filming or headless running)** — read **`docs/RIG.md`**: two flows over one primitive (`scripts/ops/capture_rig.sh`) — **film** (staged scene + moving camera + `sustain_live.py` loop + `scripts/rig/{record,encode,teardown}.sh`) and **run** (boot ONE client headless via `-K`, drive over the bridge, no camera). Stop rig clients with `scripts/rig/teardown.sh`, not `pkill -f`. The `/gerda-film` + `/gerda-run` skills (`.claude/skills/`) wrap it; machine names come from `local.config.json`.

### Finding Forge SRG names (`m_7583_`, `f_92095_`) — OFFLINE, never trial-call in-game

The runtime uses **Mojang class names but SRG member names**. **Do NOT** guess by calling candidate `m_…_` names in-game — that runs on the render thread, can trip the EventLockWatchdog and drop the world. Full guide: `docs/EXTENDING.md` § SRG-mapping workflow.

> **⚠️ Raw fields are SRG too, and read as `undefined` by Mojang name — never diagnose game state with them.** In `jeval`, `Client.getMinecraft().level` / `.player` / `.screen` are SRG fields (`f_91073_`…). GraalJS resolves Java fields by their real (SRG) name, so `mc.level` is `undefined`, and `undefined != null` is **false**: a probe like `mc.level != null` reports "no world" **regardless of the true state**. To ask "is the client in the world / what screen is open", use the **SRG-free jsMacros facade**: `Player.getPlayer() != null` (in-world), `World != null`, `Hud.getOpenScreenName()` (`null` in-world), or the bot's own `get_state`/`inventory` commands. If you must read a raw field, resolve it via `srg('Minecraft','level')` (fields work too).

- `python scripts/dev/srg.py LocalPlayer respawn` → `m_7583_` (Mojang→SRG); `--rev m_7583_` → `respawn`; `--class FoodData` → full table. Resolves from the launcher's on-disk mappings (no download). Run `--build` once to cache.
- **`reflect {expr, filter?, mojang?}`** bridge command (ext.js) — live class dump with each SRG name annotated with its Mojang name (`m_38705_ →setFoodLevel`). After a game/version change regenerate the map: `python3 scripts/dev/srg.py --export harness/srg_names.json`, then `just sync`. At boot, main.js checks every hardcoded token against that map; `diag` reports the result as `srgCheck`.
- `scripts/dev/decompile.sh mc` (or `mod <name>`) — Vineflower-decompile the MC/mod jar to **Mojang-named** source (SRG tokens rewritten via `srg.py --remap`; `--raw` keeps SRG). Needs the flake dev shell (`vineflower`+`jdk21`). Output gitignored under `decompiled/`.

## Architecture: layered TS kernel behind a service harness

Human-facing map: `docs/ARCHITECTURE.md`.

The build emits one bundle that the always-on jsMacros services eval-load:

```
bridge_ctl.py / MCP "mc" ──TCP:55544──► bridge.js ──GlobalVars──► main.js ──eval──► worker.js ──runs──► dist/__gerda_bot.bundle.js (globalThis.Module)
```

**Service harness** (`harness/`, plain jsMacros Services, NOT bundled — deployed as-is):
- **bridge.js** — thin TCP gateway (default **127.0.0.1:55544**, newline-framed JSON; override host via the `mc_bridge_host` GlobalVar). No logic; queues commands into `GlobalVars`, relays responses. Restarts main.js cleanly if main's heartbeat stalls.
- **main.js** — always-on supervisor + **stable utility/API-access container** (stateless primitives the AI drives directly; stateful game logic like "drill down until vein" belongs in the bot). Owns `safeEval`, ServiceManager lifecycle, the **ext plugin registry**, and bridge dispatch (`status`, `get_state`, `diag`, `scan`, `inventory`, `get_logs`, `start/stop/halt`, `reload_worker`, `pause/resume`, `goto`, `chat`, `eval`, `jeval`, `load`, `reload_ext`, `reload_main`, the eyes/hands primitives). Tracks worker heartbeat. **`eval` is sandboxed** (World/Player only, no `Java`); **`jeval` is the privileged escape hatch** — full jsMacros/Java scope (`Java.type`, `Client`, mod APIs), loopback-only, and it rejects code that would block the render thread. Use `jeval` to drive mod Java APIs directly (FTB Quests `SubmitTaskMessage`/`ClaimRewardMessage`, EMI, GTCEu) instead of adding a one-off handler. Quest/reward ids are 16-hex unsigned longs → `java.lang.Long.parseUnsignedLong(hex,16)`. In `jeval`, call raw vanilla methods by Mojang name via the ext.js global **`srg(class,member)`** (`raw[srg('Player','getFoodData')]()`) instead of pasting `m_…_` tokens — it inverts `srg_names.json`, throws on unknown, and resolves inherited members under their declaring class. `dispatch()` routes `HANDLERS[type]` → `EXT[type]` (ext.js) → worker passthrough. main.js is **stable infra — rarely reloaded**; new mod commands go in ext.js. **Reload main.js without the GUI**: after editing + `./gerda sync`, send **`reload_main`** — it defers `ServiceManager.restartService("main")` on a background thread (the response flushes first); the worker keeps running. A brand-new container command needs one bootstrap restart first, since the running main.js does not know it yet: `jeval` `new java.lang.Thread(JavaWrapper.methodToJava(function(){java.lang.Thread.sleep(1000); JsMacros.getServiceManager().restartService("main");})).start()`.
- **ext.js** — **reloadable mod-API plugin layer** (NOT bundled). Each plugin self-registers via `register(name, fn(req,id), meta)` or the `defineCmd` wrapper; one IIFE so helpers stay private and re-eval replaces them cleanly. Examples: `emi_search`/`emi_recipe`/`emi_uses`, `prospect`, `markers`, `reflect`, `quest_complete`/`quest_claim`, the storage and waypoint commands, the `cam_*` camera commands. **Iteration loop = edit ext.js → `./gerda sync` → `reload_ext` (re-evals into a fresh `EXT` registry, rollback-on-error) — no main.js restart.** The registry is reset, not additive: removed/renamed commands disappear on reload. Globals available to plugins: `Java, World, Player, Hud, Chat, Client, KeyBind, JavaWrapper, writeResp, register`. Each plugin carries its own "how this was derived" SRG/reflection comment.
  - **`prospect {want?, keep_open?}`** — full HV-prospector cycle as ONE command: holds the prospector → opens the LowDragLib GUI → waits for the async scan to settle (`items.size()` stable) → reflects vein data out of `ProspectingMapWidget.texture.data` (player-centred grid, ~1 block-column/cell, surface-projected X/Z) → appends to the `mc_markers.json` cache → closes. Returns `resources[]` + nearest vein per ore intent. **`markers {ore?, near?}`** queries that cache (dedup'd, sorted by distance), so "walk around + re-`prospect`" builds a vein map the bot mines from. Vein-name→ore-intent map is `PROSPECT_ORE_GROUPS` (galena = silver+lead).
- **worker.js** — managed Service that `eval`s the bundle, reads its `Module` interface (`init/tick/command/stop/onChat`), drives it tick by tick, writes a heartbeat. Mirrors the world signature main.js publishes (`mc_world_sig`) into `globalThis.__MC_WORLD_SIG` for the bundle — `FWorld.getDimension` is pinned to main.js's thread, and calling it from the worker thread deadlocks.
- **ipc.js / world_store.js / screen.js / safe-io.js** — shared eval-included modules, included by main.js (and ext.js) like a poor-man's `require`: ipc.js = GlobalVars-key + envelope SSOT (mirrors `src/core/ipc/ipc.ts`); world_store.js = `mc_world.json` read-modify-write shared by main.js + ext.js; screen.js = the eyes/hands primitives merged into main.js's `HANDLERS`; safe-io.js = the dispatch-routing decision + SRG inversion and boot self-check, a plain-JS twin of `src/shared/harness/` that `test-ts/harness-contract.test.ts` holds in lockstep.
- Inter-service messaging is entirely via `GlobalVars` keys (`mc_bridge_*`, `mc_worker_*`); see `docs/IPC.md`.

**TS kernel** (`src/`, the bot logic — this is where you work). Three tiers; imports only point DOWN — **CORE < SHARED < BOT** (the defensive checker enforces it):
- **`src/core/`** — mandatory for any fork: the jsMacros/Java boundary (`runtime/`), the IPC envelope SSOT (`ipc/`), dependency-free primitives (`prim/`). Pack-agnostic.
- **`src/shared/`** — the à-la-carte engine: kernel, navigator, pure domain, config schema, harness twins, reflexes. May import `core/`, never `bot/`.
- **`src/bot/`** — Gerda Bot itself: capabilities, missions, plans, orchestrator, pack profile, entry wiring. The only tier that knows about GregTech.

Key modules:
- `core/runtime/` — the ONLY abstraction over jsMacros. `Runtime.ts` (typed boundary), `jsmacros/` (real impl split by facet — the only code allowed to touch the globals in `types/jsmacros.d.ts`; `jsmacros/srg.ts` is the one home for SRG tokens in `src/`), `mock.ts` (in-memory; implements the SAME interface, so it can't drift).
- `shared/kernel/` — `fsm.ts` (declarative validated transitions), `mission.ts` + `mission-registry.ts`, `sequencer.ts`, `progress.ts` (progress watchdogs), `slice.ts` (typed blackboard slices), `logger.ts` (NDJSON sink + `recent()` ring buffer backing `get_logs`), `lifecycle.ts`, `bus.ts` (typed event bus), `capability.ts` (tick pipeline + Ctx + registry).
- `bot/profile/states.ts` — the `STATE` table, `TRANSITIONS`, `GLOBAL_EDGES` and `UNIVERSAL_TARGETS` (HOME/PAUSED/ERROR/…).
- `bot/capabilities/` — always-on plugins: `core` (lifecycle + IDLE), `maintenance` (resumable interrupts such as EAT), `recover`, `persistence`, `hud`, `telemetry`, `diagnostics` (`smoke`), `nav-probe`, `nav-engine`, `sensors`, `event-export`, `mission-control`, `chat-command` (in-game `!<bot> <verb>` driving — queued off-thread, drained on the tick thread; trust list off by default). Each declares FSM edges / a pre-dispatch `guard` / per-phase `handlers` / `commands`.
- `shared/reflexes/` — vitals, air, hunger, tool, stuck, hazard, human-input (→ PAUSED), swim-out, water-clutch, death; which of them run while IDLE: docs/SAFETY.md § Reaction tier.
- `bot/missions/` — one directory per mission. `mine/` holds the mission-scoped caps it composes: `scan`, `navigation` (GOTO via the greedy executor), `mine` (async break + vein continuation), `loot`, `inventory`, `home-return`, `storage`.
- `shared/nav/` — the navigator (the sole movement driver), behind the `@/nav` barrel: `core` (step type, sprint control, key release), `supply` (filler/bucket/peer seams), `descent` (recoverability guard), `route` (world-view cache + A* route cache + D* Lite + commit-to-choice), `ladder`/`pillar`/`parkour` (sub-machines), `executor` (`greedyStep` + walk/mine/bridge drives), plus `break-cell`/`place-cell` and the `engine` selection slice.
- `shared/domain/` — pure, jsMacros-free, unit-tested: `planner`, `dstar`, `scan`, `solveMiningTarget`, `tooling`, `inventory`, `vein`, `world-view`, …
- `shared/config/schema.ts` — typed, nested `Config` SSOT + `DEFAULT_CONFIG` (`cfg.section.key`). **All tunables live here.** A gitignored `config/local.overrides.json` deep-merges over it at build time.
- `bot/entry/worker-bundle.ts` — wires runtime/kernel/capabilities/missions and assigns `globalThis.Module`.

## Conventions

- **Tunables live in `src/shared/config/schema.ts`.** A magic number in capability/domain logic is a bug. Every `cfg.<key>` / `cfg.<section>.<key>` written anywhere in the tree (code, comments, docs; a historical doc opts out with a `<!-- cfg-drift: historical -->` line, only if its basename is in the test's `HISTORICAL_ALLOWED`) must resolve in `DEFAULT_CONFIG` — `test-ts/cfg-keys-drift.test.ts` fails the commit otherwise.
- Timing is in ticks (20 ticks = 1 second).
- Anything touching jsMacros goes through the `Runtime` facade so it stays testable against `mock.ts`. Domain code takes plain data, never the runtime.
- Fail loud: fallible reads return `Result`; never fabricate a fallback. The defensive checker rejects `try/catch`, `as` casts and dropped `Result`s outside designated boundaries.
- Tests are **vitest** in `test-ts/`: pure domain + capability/mission loops on the mock runtime. Live behaviour is covered by the arena gate (`just gate-live`), not by vitest.
- Adding a capability = one module + registering it in `bot/entry/worker-bundle.ts`; no kernel edits.
- Mission names/params must appear in `docs/MISSIONS.md` — `test-ts/docs-drift.test.ts` fails the commit otherwise.

## MCP

The `mc` stdio MCP server lives at `mcp/server.py` (self-contained; `uv run mcp/server.py`), wrapping the bridge over `MC_BRIDGE_PORT=55544` — wire it via `.mcp.json` (gitignored; copy `.mcp.json.example`). The `mcp__mc__mc_*` tools (`mc_ping`, `mc_get_state`, `mc_send`, `mc_fleet_*`) are the preferred way to inspect/drive a live bot; everything without a dedicated tool goes through `mc_send` (discover commands via the `mc://api` resource). The canonical `BridgeClient` is `mcp/bridge_client.py`; scripts import it directly — each puts the repo's `mcp/` dir on `sys.path` in its bootstrap.

## Eyes & hands: screenshots + GUI clicks (the AI driving the game directly)

Game instance: `<instancesRoot>/<humanInstance>/minecraft` (call it `$INST`; `humanInstance` is a `local.config.json` key, default `Monifactory`; `$INST` = `$(python3 scripts/local_config.py instance_dir <name>)/minecraft` — `instance_dir` returns the launcher folder, the game dir is its `minecraft/`; the root comes from env `MC_INSTANCES_ROOT` > `local.config.json` `instancesRoot` > launcher autodetect). Bridge: `127.0.0.1:55544` — `mcp/bridge_client.py` probes loopback first, so no `--host` needed. These primitives are container handlers (full jsMacros access) reachable via `mc_send` / `BridgeClient().send(...)`. The eyes/hands ones (screenshot/read_screen/click/scroll/type/keypress/introspect/close_screen) live in **`harness/screen.js`** (eval-included, merged into `HANDLERS`); their help metadata stays in main.js's `META_COMMANDS`.

**Eyes — `screenshot` → `scripts/ops/mc_shot.py`.** The `screenshot` command calls native jsMacros `Player.takeScreenshot` (on the render thread) → writes `$INST/screenshots/ai_shot.png` (deterministic, overwritten). It works on ANY GUI, including custom-rendered ones, and **while MC is unfocused/off-screen** — but ONLY with `enableVsync:false` in `options.txt` (otherwise the off-screen window stops rendering and the frame goes stale). Read it host-side: `python3 scripts/ops/mc_shot.py --file -s 0.4 [-g "X,Y WxH"]` (ffmpeg resize/crop → `/tmp/mc_shot.png`, then `Read` it). It reads the HUMAN instance by default — set `MC_INST=<instances>/<inst>/minecraft` for another instance, or you get a stale frame. **Token cost scales with PIXELS, not bytes** — downscale with `-s` (0.5≈1200tok, 0.33≈530, 0.25≈300) and crop with `-g` (~100tok); jpeg doesn't help. Also: `--latest` (newest F2 shot), or bare mode = host-compositor `grim` (Wayland-only; needs MC visible — the in-game `screenshot` command is the portable path). Framebuffer = the MC window size, NOT the monitor. The `÷4` below assumes `guiScale:4` in the instance's `options.txt`; divide by your instance's `guiScale`.

**Hands — `click` / `scroll` / `type` / `keypress` / `key`.** `click {x,y,button}` calls the REAL vanilla `Screen.mouseClicked`/`mouseReleased` (Forge SRG `m_6375_`/`m_6348_`); `scroll {x,y,amount}` = `m_6050_`, `type {text}` = `charTyped` `m_5534_` per char, `keypress {code}` = `keyPressed`/`Released` `m_7933_`/`m_7920_` (Enter=257 Backspace=259 Esc=256). **Coords are GUI-scaled = screenshot-pixel ÷ guiScale (÷4).** Re-find SRG by signature (mouseScrolled is the unique `(double,double,double)`, charTyped `(char,int)`, etc.) or mappings.dev/Linkie under `GuiEventListener`; `introspect {target:"screen"}` lists the live `m_…_` names. Do NOT use `jsmacros_mouseClicked` — it only drives jsMacros' own overlay and never reaches the real screen.

**Input works per GUI framework:**
- **Vanilla** screens (containers, buttons, anvil/sign text fields) and **FTB-Library** (FTB Quests book): synthetic `click`/`scroll`/`type` work with the PASSED coords, **no OS cursor, no window focus** — FTB's `ScreenWrapper.mouseClicked` calls `updateMouseOver(x,y)` first. FTB Quests is fully drivable headless (click a quest node, scroll the tree).
- **EMI/JEI overlays** (item index + search bar) hit-test the **real OS cursor** and hook the keyboard at `KeyboardHandler` (below `Screen.charTyped`), so synthetic `type`/`click` do NOT reach them. Use EMI's **native Java API** instead (next section). (Last resort for clicking an EMI cell: focus the MC window and `xdotool mousemove <px> <py> click 1` in framebuffer pixels — on a Wayland desktop MC runs under Xwayland, and an unfocused warp fails.)

**EMI without screenshots/cursor/focus — its native Java API.** EMI's `dev.emi.emi.*` classes are NOT SRG-remapped on Forge, so `harness/ext.js` calls them by real name:
- `emi_search {text, limit?}` — **fully headless**: `EmiApi.setSearchText()` + `EmiSearch.update()`, waits ~8 ticks for EMI's async search, returns matching **item ids as data** (`results: ["minecraft:iron_ingot", …]`). Full EMI query syntax works (`@gtceu raw`, `#ore`, tooltips). This is the way to look up what items exist — never screenshot the item panel.
- `emi_recipe {item}` — opens the recipe GUI for what CRAFTS it (`EmiApi.displayRecipes(EmiStack.of(...))`). `emi_uses {item}` — where it's USED (`displayUses`). These open a Screen (main thread) — screenshot to read the grid.
- Item id → `EmiStack` is built SRG-free via jsMacros' `new ItemStackHelper(id,1).getRaw()`. Pure reads (`getSearchText`, `EmiSearch.stacks`, `getIndexStacks`) need no main thread; `display*`/`setSearchText` do. `EmiSearch.stacks` is async-populated — wait before reading.

`click {i}`/`{text}` clicks a standard button widget by index/label. `key {key}` taps a keybind (`key.use` opens the held item, `key.inventory`, …). `read_screen` sees only standard widgets — BLIND to custom GUIs (FTB/EMI); use screenshots there. Reliable loop: screenshot → tight `-g` crop to pin the pixel center → `÷4` → `click` → screenshot to verify.

**FTB Quests:** the book GUI is custom (`read_screen` shows `open:true, title:'', buttons:[]`). Read the quest tree from disk instead of guessing: `$INST/config/ftbquests/quests/chapters/*.snbt` (ids, x/y grid pos, `dependencies`, task `type`, items), and resolve `{moni.task.*}`/`{moni.quest.*}` title keys via `$INST/kubejs/assets/ftbquests/lang/en_us.json`. `checkmark`-type quests complete on a click; item-type tasks auto-detect when you hold the item.
